# COCO Rotation Benchmark

Protocol v1.

A test for image rotation angle estimation over the full circle that any model can be scored on.
It fixes the photos, the rotation angles and the way the test images are built, so that every model sees the same pixels.
It also contains a check that a score comes from the image content and not from traces that the rotation leaves in the pixels.

The test images are those of the COCO evaluation in the paper ([arXiv:2603.25351](https://arxiv.org/abs/2603.25351), version 2), so the COCO results reported there are results under this protocol.

## Photos

- 1,030 upright photos from COCO val2014: the images with label 1 or 2 in the list of Fischer et al. (2015), as described in [data/DATASETS.md](data/DATASETS.md).
- Their file names and SHA-256 checksums are in [eval/benchmark/photos.sha256](eval/benchmark/photos.sha256). The benchmark script refuses to run on other files.
- 915 of the photos are also part of COCO train2017. A model trained on COCO 2017 has to be trained without them (`data/datasets/remove_test_images.sh`).

## Test images

Each photo is rotated by a random angle and cropped, which gives one view.

- **Angles.** Five sets, with seeds 0 to 4. For seed `s`, the angles are `numpy.random.seed(s)` followed by `numpy.random.uniform(0, 360, 1030)`. The i-th angle belongs to the i-th photo of [eval/test_order/test_coco.txt](eval/test_order/test_coco.txt).
- **Rotation.** The photo is rotated counter-clockwise by the angle about its centre with bilinear interpolation on an enlarged canvas (OpenCV `warpAffine`).
- **Crop.** The rotated photo is cropped at its centre to the largest upright rectangle that contains no border. The view keeps this size. Resizing is part of the model.
- **Two forms.** In the form *saved as JPEG*, the view is saved once as JPEG at quality 90 (Pillow, 4:2:0 chroma subsampling) and decoded again. In the form *not re-encoded*, the view is used as rendered.

This gives 5,150 views per form.
The form saved as JPEG is the primary one, because a rotated photo that exists as a file has been saved after the rotation.
The second form shows how a model behaves on rotations that are applied in memory or stored without loss.

The reference implementation is `rotate_array_preserve_content(image, angle, mode="crop")` and `jpeg_roundtrip(view, 90)` in [rotation_utils.py](rotation_utils.py).

## Task

The model receives one RGB image and returns one angle: the counter-clockwise rotation of the image content in degrees.
Rotating the image by the negative of this angle turns it upright.
The model gets nothing else, in particular no file name and no metadata, and it answers every view.
A model that can abstain is scored with abstention switched off.

## Scores

The error of a view is the circular distance between the predicted and the true angle, with both taken modulo 360°, so it lies between 0° and 180°.

For each of the five sets of angles, the following statistics are computed over all 1,030 views:

- mean absolute error (MAE), median, 90th and 95th percentile, root mean square error
- share of views with an error of at most 2°, 5° and 10°
- number of upside-down answers, which are errors of 150° or more

The reported value of a statistic is its mean over the five sets.
The number of upside-down answers is reported as the total over all 5,150 views.
The headline numbers are the MAE and the share within 10° on the views saved as JPEG.

## Check for processing traces

A decoded JPEG photo carries the 8x8 block grid of the codec, and the grid turns with the photo when it is rotated.
The interpolation of the rotation leaves a pattern of its own.
A model can read the angle from such traces without looking at the content, which gives a high score on the benchmark and a model that fails on other images.
A re-encoded test image does not rule this out, because a strong grid in the source photo partly survives the second save.

The check therefore uses images without any content.

- **Textures.** 1,000 isotropic noise textures of 640 x 480 pixels, generated by `make_texture` in [eval/grid_probe.py](eval/grid_probe.py) from `numpy.random.default_rng(0)`, followed by 1,000 angles from the same generator.
- **Conditions.** Each texture is rotated and cropped like a photo, in seven conditions. In `lossless`, `jpeg90`, `jpeg75` and `jpeg50` the texture is used as generated or saved as JPEG at that quality before the rotation, and the view is not re-encoded. In `lossless/jpeg90`, `jpeg95/jpeg90` and `jpeg75/jpeg90` the view is in addition saved as JPEG at quality 90 after the rotation, like the primary test form.
- **Statistics.** A grid has four-fold symmetry, so it reveals the angle modulo 90°. The first statistic is the share of predictions within 5° of the true angle modulo 90°, which is 11.1% by chance. The second is ρ₄, the mean of cos(4 (predicted - true)), which is 0 for a model that ignores the grid and 1 for a model that follows it.
- **Criteria.** A condition is passed if the upper bound of the 95% bootstrap interval of ρ₄ is at most 0.20 and the upper bound of the share minus chance is at most 5 points (2,000 resamples, generator seed 1).

A result states how many of the seven conditions are passed.
The limit of 0.20 for ρ₄ is the one that ORTUS AI uses for its RightWayUp models.
ORTUS AI also identified the block grid as a cue in the first place.

## What a result states

- the name of the model, its number of parameters and its input size
- the training data, and for COCO 2017 whether the 915 test photos were removed
- the scores on both forms and the number of probe conditions passed
- the library versions, and whether the images were bit-identical to the reference rendering

The script writes all of this to one JSON file, together with the prediction for every view, so that two models can be compared view by view.

## Running it

The script needs `numpy`, `opencv-python-headless` and `pillow`, and whatever the model needs.
A model is connected by an adapter, a Python file with a description and a function that returns the prediction function:

```python
INFO = {
    "name": "my model",
    "parameters": 23_000_000,
    "training_data": "what it was trained on",
    "input": "224 x 224 pixels",
}

def load():
    model = ...                      # load the model once

    def predict(image):              # image: PIL.Image.Image, RGB
        return ...                   # counter-clockwise angle in degrees

    return predict
```

```bash
# a quick check with 20 photos and 20 textures, not a result
python eval/benchmark/run.py --adapter my_adapter.py --limit 20 --out smoke.json

# the benchmark
python eval/benchmark/run.py --adapter my_adapter.py --out my_model.json

# the released model of this repository, from the Hugging Face Hub
python eval/benchmark/run.py --adapter eval/benchmark/adapters/released_model.py --out result.json

# a checkpoint trained with this repository
python eval/benchmark/run.py --approach cgd --ckpt path/to/checkpoint.ckpt \
  --training-data "COCO 2017 train without the test photos" --out result.json
```

The model is called once per image, 17,300 times in total.

## Reference rendering

The pixels of a view depend slightly on the versions of OpenCV and Pillow, because their interpolation and JPEG code round differently between versions.
[eval/benchmark/reference.json](eval/benchmark/reference.json) holds one hash per set of images for the reference rendering.
It was made with Python 3.12.11, numpy 2.2.6, opencv-python 4.12.0.88 and Pillow 11.3.0 (libjpeg-turbo 3.1.1).
The script compares its own rendering with these hashes and reports the outcome.
With the same library versions the images are bit-identical, which a second run confirmed.

Other versions change the scores very little.
With OpenCV 5.0.0 and Pillow 12.3.0, no image set was bit-identical to the reference, and the MAE of one model differed by at most 0.04° from its MAE on the reference rendering.
A probe condition that a model meets or misses by a narrow margin can still change sides, so a result that is meant to be compared with others should come from the reference versions.

## Results

Means over the five sets of angles, on the reference rendering.
The result files with all statistics and the prediction for every view are in [eval/benchmark/results/](eval/benchmark/results/).

| Model | Parameters | MAE, saved as JPEG | Within 10°, saved as JPEG | MAE, not re-encoded | Within 10°, not re-encoded | Probe conditions passed |
|---|---|---|---|---|---|---|
| CGD + ConvNeXt V2 Base, COCO 2017, trace-free protocol (released model) | 88M | 3.71° | 97.3% | 4.38° | 95.9% | 7 of 7 |
| CGD + MambaOut Base, COCO 2017, conventional protocol (legacy model) | 83M | 24.45° | 30.5% | 2.84° | 98.0% | 4 of 7 |

The legacy model shows what the check is for.
It has the best score in the table on the views that are not re-encoded, and it fails the probe: on noise textures with a quality-50 grid, 96% of its predictions are within 5° of the true angle modulo 90°, although the textures show nothing.
On the views saved as JPEG its error is 24.45°.

The released model decodes the angle as the circular mean of the bins within 10° of the most probable bin.
With argmax decoding, as used in the paper, the same checkpoint gives 3.77° and 4.45°.
